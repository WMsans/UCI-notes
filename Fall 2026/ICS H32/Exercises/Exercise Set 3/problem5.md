# Problem 5

These three functions are the internal plumbing of the implementation of the Polling protocol. These functions are protected in order to ensure that the public API of the module is kept minimal and that nobody is using them inadvertently. If these were made public, the users of the module may accidentally use them incorrectly, whether by using `_read_line` rather than `questions()` or `results()`, thus circumventing the validation performed by these functions (which raises `PollingProtocolError` or `NoSuchQuestionError` in case the server does something out of the ordinary). Protecting these functions also makes sure that I can change the way the module communicates with the socket (how the connection is represented, how the newline sequence is dealt with, how the debug trace is performed) without having to worry that someone else's module has begun to depend on these details, because the public functions (`hello`, `questions`, `choices`, `vote`, `results`, `goodbye`, `connect`, `close`) isolate their callers from that.
